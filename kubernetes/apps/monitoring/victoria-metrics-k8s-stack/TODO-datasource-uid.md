# TODO: pin VictoriaMetrics Grafana datasource UIDs

## Problem

Josh reported that after updating `victoria-metrics-k8s-stack`, Grafana
dashboards break because the datasource's provider ID (UID) changed.
Dashboards reference a datasource by UID, so if it changes, every panel
loses its data source.

## Root cause

`grafana-operator` (v5.24.0, deployed via
`kubernetes/early/grafana-operator/helm-release.yaml`) resolves the
Grafana-side UID for a `GrafanaDatasource` CR with this precedence
(source: `api/v1beta1/grafanadatasource_types.go`, `GetGrafanaUID()`,
tag `v5.24.0`):

```
spec.uid (CustomUID)  >  spec.datasource.uid (deprecated)  >  metadata.uid
```

`metadata.uid` is the Kubernetes object's own random UID — it changes if
the `GrafanaDatasource` object is ever deleted and recreated (as opposed
to patched in place).

The `GrafanaDatasource` CRs for VictoriaMetrics are auto-generated by the
`victoria-metrics-k8s-stack` chart via
`defaultDatasources.grafanaOperator.enabled: true`
(see `templates/grafana/datasource.yaml` in the chart, and
`kubernetes/apps/monitoring/victoria-metrics-k8s-stack/helm-release.yaml`
in this repo). The chart's own `values.yaml` currently pins:

```yaml
defaultDatasources:
  victoriametrics:
    datasources:
      - name: VictoriaMetrics
        type: prometheus
        access: proxy
        uid: VictoriaMetrics
        isDefault: true
      - name: VictoriaMetrics (DS)
        isDefault: false
        access: proxy
        uid: VictoriaMetricsDS
        type: victoriametrics-metrics-datasource
```

Those `uid:` values feed into `spec.datasource.uid`, which per the
precedence above **should** already be stable. But this is a chart
default we don't control — nothing in our own
`victoria-metrics-k8s-stack/helm-release.yaml` pins it, so a future chart
version could rename/remove those `uid` fields (or a version in the past
did, which may be what caused the breakage Josh already saw), silently
falling back to the random `metadata.uid`.

## Fix

Pin the datasource list explicitly in our own values, in
`kubernetes/apps/monitoring/victoria-metrics-k8s-stack/helm-release.yaml`,
so it's under our control and any future change is a visible diff in
this repo rather than a silent upstream chart change:

```yaml
defaultDatasources:
  grafanaOperator:
    enabled: true
  victoriametrics:
    datasources:
      - name: VictoriaMetrics
        type: prometheus
        access: proxy
        uid: VictoriaMetrics
        isDefault: true
      - name: VictoriaMetrics (DS)
        isDefault: false
        access: proxy
        uid: VictoriaMetricsDS
        type: victoriametrics-metrics-datasource
```

## Steps to implement

1. **Check what's actually live first** — don't blindly apply the pin
   above, confirm it matches reality or you'll break things again:

   ```bash
   kubectl get grafanadatasource -n monitoring \
     -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.uid}{"\n"}{end}'
   ```

   - If `status.uid` already reads `VictoriaMetrics` / `VictoriaMetricsDS`
     for the corresponding datasources, the override above is safe to add
     as-is.
   - If it shows something else (a random string like a UUID), use that
     value in the override instead — the goal is to freeze the *current*
     UID, not necessarily rename it to `VictoriaMetrics`.

2. Add the `defaultDatasources.victoriametrics.datasources` override
   under `values:` in
   `kubernetes/apps/monitoring/victoria-metrics-k8s-stack/helm-release.yaml`
   (it currently only has `defaultDatasources.grafanaOperator.enabled: true`,
   around line 35-37).

3. Reconcile flux and confirm the `GrafanaDatasource` CRs still show the
   same `status.uid` as step 1 (no change expected — this step is purely
   defensive/pinning, not a UID change).

4. Check any existing Grafana dashboards that reference these datasources
   by UID (Administration → dashboards, or grep dashboard JSON for
   `"uid": "<value-from-step-1>"`) and confirm panels still resolve.
   If step 1 revealed a mismatch and you had to pick a *different* UID
   than `VictoriaMetrics`/`VictoriaMetricsDS`, existing dashboards may
   need their datasource re-pointed once, after which this fix keeps it
   stable going forward.
